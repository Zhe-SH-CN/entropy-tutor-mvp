# 系统架构

## 设计目标

系统围绕三条主线设计：

1. **交易与履约闭环**：从有效需求到候选、见面、订单、课次、报告和续课反馈，状态可由数据库和事件共同核验。
2. **教师负责的 AI 辅助**：模型生成结构化建议，教师审核后才形成家长可见交付。
3. **可解释、可回放的匹配**：推荐由确定性规则执行，保存输入和评分证据，仅使用可信履约行为更新特征。

首版不拆分为微服务，不引入独立消息队列、特征平台或 Kubernetes。

## 逻辑视图

| 模块                     | 职责                                                          |
| ------------------------ | ------------------------------------------------------------- |
| `apps/web`               | 三角色响应式界面、同源 API 入口、候选可见曝光采集             |
| `apps/api`               | 认证授权、业务状态机、推荐、AI 网关、沙箱支付与会议、分析查询 |
| `apps/api/src/worker.ts` | 邀请过期、任务领取、有限重试、退避和死信                      |
| `packages/shared`        | 需求与教师合同、推荐类型、纯函数评分与过滤                    |
| `prisma`                 | 数据模型、事务约束、迁移和合成种子                            |
| `compose.yaml`           | Web、API、Worker、迁移任务和 PostgreSQL 编排                  |

## 请求与数据路径

1. 浏览器仅请求同源 `/api/v1`。
2. Next.js 服务端将请求转发到 NestJS，避免在客户端固化内网 API 地址。
3. NestJS 完成输入校验、会话认证、CSRF 校验、角色和资源授权。
4. Prisma 在 PostgreSQL 中执行事务读写；关键业务事实同时写入领域事件。
5. Worker 从同一数据库领取到期工作，不引入第二套状态存储。
6. AI 请求通过服务端 Model Gateway，密钥和供应商配置不进入浏览器持久存储。

## 核心领域模型

| 聚合           | 关键实体                                              |
| -------------- | ----------------------------------------------------- |
| 身份与师资     | User、Session、Teacher、ModelConfig                   |
| 需求与匹配     | Demand、RecommendationRun、Invitation、ManualOverride |
| 见面与教学关系 | Meeting、Relationship                                 |
| 订单与课次     | PaymentOrder、PaymentEvent、Lesson                    |
| AI 与学习证据  | Artifact、LearningState                               |
| 反馈与运营     | ParentFeedback、EventLog、Job                         |

### 需求与邀请

- 需求由草稿进入 Mock 结构化，再由家长确认；只有已确认需求可以推荐。
- 仅审核通过且可用性仍在有效期内的教师进入候选。
- 邀请支持接受、拒绝和到期；到期由系统记录，不混同为教师主动拒绝。

### 见面与关系

- 双方分别提交继续意愿。
- 双方都选择继续后才建立教学关系。
- 改期、取消和 no-show 作为独立事实追加，不回写为成功见面。

### 课次与履约

- 教师记课后，课次进入待确认状态。
- 家长或运营确认后，课次才进入正式完成口径。
- 取消和 no-show 不占同师正式课序号。
- 完成确认触发教师可信履约聚合更新。

### AI Artifact

- 备课卡、学习状态和课后报告均保留草稿与审核轨迹。
- 学习状态从 `unverified` 进入 `teacher_confirmed` 后才可用于后续教学。
- 报告只有教师确认版对家长可见；发送和已读分别记录。

## 推荐架构

推荐入口执行：资格过滤 → 特征收缩 → 七项评分 → 负载与探索约束 → Top 3 → 快照持久化。

```text
FinalScore = 40P + 20E + 20R + 20C - 10B - 10L² + X
```

- `P`：家长目标适配。
- `E`：报价与教师目标毛时薪适配。
- `R`：时间与履约可靠性。
- `C`：历史持续上课表现。
- `B`：通勤与备课负担。
- `L`：当前负载，采用平方惩罚并在满载时硬过滤。
- `X`：受配额约束的新教师探索奖励。

历史指标使用先验收缩，避免小样本极端化。LLM 情绪词、未确认学习状态和主观教师评分不得进入排序。规则实现与测试位于 `packages/shared/src/recommendation.ts` 及相邻测试文件。

## 模型网关

支持三种明确模式：

- `mock`：确定性本地生成，用于开发和测试。
- 托管 OpenAI 兼容提供方：由服务端环境变量配置。
- `BYOK`：教师提供 OpenAI 兼容端点和密钥。

BYOK 密钥使用 AES-256-GCM 加密，读取接口不返回明文。Base URL 仅允许 HTTPS 和公网解析地址，并限制重定向、超时和响应大小。真实供应商的可用性、成本和质量不属于代码级保证。

## 外部适配器

支付和会议采用适配器边界，当前实现为沙箱：

- 订单和支付回调具有幂等约束与事务处理。
- 会议地址使用保留的 `.invalid` 域名。
- 接入真实供应商前，必须重新验证签名、回调顺序、退款、超时和故障恢复。

## 事件与审计

事件采用追加式记录，包含公共字段、实体关联、幂等键和规范化属性。详细内容保存在受控业务表，事件仅保存可分析的状态和引用。完整定义见[事件字典](event-dictionary.md)。

## 部署拓扑

单主机部署由 PostgreSQL、一次性迁移任务、API、Worker 和 Web 组成。Web 是唯一需要反向代理到团队访问入口的应用服务；数据库不公开端口，API 默认仅绑定回环地址。详见[部署指南](deployment.md)。
